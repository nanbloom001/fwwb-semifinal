# p06 相似性风险审计与独立重构计划

日期：2026-05-29

## 文档目的

本文用于指导对以下三份代码进行系统审计：

- 参考代码：`/Users/nanbloom001/fwwb-RL-dog/代码归档/xtrack9`
- 官方模板：`/Users/nanbloom001/fwwb-RL-dog/代码归档/最新版本官方原始代码`
- 当前版本：`/Users/nanbloom001/fwwb-RL-dog/代码归档/p06`

目标不是做表面层的“混淆”或规避查重，而是完成一套可落地、可解释、可复核的独立实现整理工作：

1. 找出 `p06` 中从 `xtrack9` 继承但当前没有使用、可以删除的代码。
2. 找出 `p06` 相对官方模板的敏感改动，尤其是可能被官方误判为利用漏洞、绕过限制、读取不当信息或修改不当协议的实现。
3. 找出 `p06` 中真实继承自 `xtrack9` 的功能模块，并制定独立重构方案。
4. 通过“删除 + 审计 + 重写 + 说明”的方式，把 `p06` 收敛为一份结构清晰、依赖明确、风险可解释的独立代码。

## 基本原则

### 合规边界

本计划不包含以下内容：

- 仅为了降低查重率而进行的函数改名、变量改名、注释伪装、空洞重排。
- 不改变核心逻辑、只改变外表的机械式“洗稿”。
- 仅为了规避检测而保留同一实现、改变局部写法。

本计划允许并鼓励以下内容：

- 删除未使用遗留代码。
- 删除实验性、无效、不可解释的配置和面板。
- 对确实需要保留的能力进行重新设计和重新实现。
- 把策略解释从“继承某队实现”转为“基于官方接口和我们自己的实验结论”。

### 产出原则

每一项审计结论都必须能回答四个问题：

1. 它来自哪里。
2. 它现在是否还在使用。
3. 它是否有风险。
4. 它应该删除、保留还是重写。

### 优先级原则

优先顺序固定为：

1. 先建立三方代码事实基线。
2. 再删未使用继承代码。
3. 再做敏感修改风险审计。
4. 再识别必须保留的继承功能。
5. 最后做独立重构。

不要一开始就改代码。先把事实矩阵建立完整。

## 前置任务：先用 p06 覆盖当前仓库

### 目标

在开始三方审计前，先把：

- `代码归档/p06`

作为工作基线覆盖到当前仓库工作目录，确保后续所有审计、删除、重构和验证都针对同一份代码开展。

### 原因

如果当前仓库仍停留在旧状态，后续会出现三个问题：

1. 审计对象和最终要修改的代码不是同一份。
2. 删除候选和敏感修改清单会与真实交付版本错位。
3. 后续重构结果无法直接落在最终版本上，容易返工。

### 执行要求

覆盖前必须先做最小保护，避免当前仓库的现有改动丢失：

1. 先记录当前仓库状态：
   - `git status`
   - 当前分支
   - 当前 HEAD commit
2. 对当前仓库做一次归档：
   - 可用 git commit
   - 或单独复制到临时备份目录
3. 再将 `p06` 的代码覆盖到当前仓库。
4. 覆盖完成后重新生成文件树，确认当前仓库已经和 `p06` 对齐。

### 覆盖范围

## 第一阶段：建立三方事实基线

### 目标

建立一个纯事实层面的三方代码矩阵，回答“哪些文件存在、哪些文件改了、哪些文件只出现在某一方”。

2. 只保留核心代码与配置文件。
3. 对每个路径标记三方存在状态。
4. 建立统一路径映射，处理可能的目录名差异。

### 输出格式

每一行至少包含：

- 规范化路径
- 官方是否存在
- xtrack9 是否存在
- p06 是否存在
- 文件类型
- 初步优先级

### 验收标准

执行完这一阶段后，应能快速回答：

- 哪些文件只在 `p06` 出现。
- 哪些文件是 `xtrack9` 引入而官方没有。
- 哪些文件是官方模板已有但 `p06` 被大改。

## 第二阶段：三方差异分组

### 目标

对文件做初步分类，锁定后续重点审计区域。

### 分类方式

将文件分为四类：

1. A 类：`p06` 与官方基本一致。
2. B 类：官方有，`p06` 修改较多。
3. C 类：`xtrack9` 和 `p06` 共有，官方没有或官方差异很大。

### 重点关注

### 输出

`diff_summary.md` 至少要包含：

- 文件列表
- 分类

- 初步备注

## 第三阶段：删除未使用继承代码

### 目标

找出 `xtrack9` 继承进来但 `p06` 现在不再使用的代码，并制定删除顺序。

### 判断标准

一个模块只有在满足“实际被使用”时才保留。判断方法包括：

1. 全仓库文本引用搜索。
2. Python import 引用关系。
3. TOML 是否启用对应 reward、stage、配置项。
4. workflow 是否动态调用对应函数。
5. monitor 是否还在使用对应指标。
6. 训练或评估当前路径是否会走到该代码。

### 重点删除候选

优先排查：

- 未启用的 reward 函数。
- 仅用于旧实验的 gate/probe/debug 逻辑。
- 未使用的训练配置和评估配置。
- 不再上报的 monitor 指标。
- 旧 runtime 残留文件。
- 旧 standard / old track 的实验性 TOML。
- 历史保留下来的适配器、桥接器、临时工具。

### 分类处理

每个候选项只允许落入三类：

- 可直接删除
- 先验证再删除
- 必须保留

### 输出

`delete_candidates.md` 应包含：

- 文件或函数位置
- 来源判断
- 当前引用情况
- 删除风险
- 推荐动作

`keep_reason.md` 应包含：

- 明确说明为何保留
- 保留后是否计划重写

## 第四阶段：敏感修改风险审计

### 目标

找出相对官方模板的高风险改动，并按严重程度排序。

### 高风险检查项

重点检查以下行为：

1. 是否读取了官方未公开的 terrain label / terrain level / terrain type。
2. 是否直接访问或依赖 privileged 信息来影响评估策略。
3. 是否绕过官方 `reset/step` 协议。
4. 是否篡改 `terminated / truncated / dones` 逻辑。
5. 是否通过 timeout bootstrap 或 episode 统计修改造成异常评分表现。
6. 是否修改或伪造 `completed_count / abnormal_count / timeout_count / total_score` 等统计上报。
7. 是否在评估时保留训练专属信息或训练专属 reward probe。
8. 是否直接写底层 `command_manager`，使评估行为与官方默认协议偏离。
9. 是否引入本地文件、外部通信、RPC、浏览器相关副作用影响训练或评估。
10. 是否存在 token、绝对路径、硬编码外部资源、隐藏依赖。

### 中风险检查项

以下内容未必违规，但需要重点说明：

- eval command override
- worker gate command override
- raw scanner / nav scanner 的自定义解释逻辑
- 训练期 probe 是否影响评估性能
- 删除官方配置后是否影响平台运行
- 自定义监控逻辑是否改变训练语义

### 输出格式

`sensitive_changes.md` 每项至少包含：

- 文件
- 位置
- 相对官方修改
- 风险等级
- 风险原因
- 是否来自 `xtrack9`
- 建议动作

### 风险等级定义

- `P0`：疑似违规、疑似漏洞利用、必须立即处理
- `P1`：高风险，提交前必须解释或重写
- `P2`：中风险，需要验证和文档说明
- `P3`：低风险，可保留但建议整理

## 第五阶段：识别真实继承自 xtrack9 的功能

### 目标

确认哪些实现不是“恰好相似”，而是功能、结构、阈值、命名和调用链都明显延续自 `xtrack9`。

### 识别维度

需要综合判断以下信号：

1. 函数名、类名、配置名高度一致。
2. 实现流程一致。
3. 阈值组合一致。
4. 注释结构一致。
5. reward 组合逻辑一致。
6. maze / gate / speed advice 的阶段划分一致。
7. monitor metric 命名和统计口径一致。

### 结论分类

每个继承项只能归入以下三类之一：

- 纯遗留：不再使用，删除
- 核心依赖：当前在用，但需要重写
- 通用方案：可以保留，但必须写清楚不是依赖非公开信息

### 输出

`inherited_from_xtrack9.md` 至少包含：

- 功能名称
- p06 位置
- xtrack9 对应位置
- 官方是否存在类似功能
- 当前是否启用
- 风险评估
- 处理建议

## 第六阶段：独立重构方案

### 目标

对那些“必须保留的能力”做真实重构，而不是表面改写。

### 重构原则

1. 从官方公开协议出发重新定义输入输出。
2. 删掉不必要的历史命名。
3. 删掉来源不明的中间变量和旧实验参数。
4. 把 magic number 迁回配置文件，并标注实验来源。
5. 用更清晰的模块边界表达真实功能。
6. 只保留当前训练路径需要的逻辑。

### 优先重构模块

建议优先顺序：

1. 地形门控
2. 速度建议与命令覆盖
3. maze 导航辅助
4. reward 组合与时间压力
5. 训练期 probe 与 monitor 上报

### 推荐重构方式

以地形门控为例，重构不应是“改个名字”，而应是：

1. 先写模块接口说明：
   - 输入：height scan / nav scan / proprio / goal
   - 输出：terrain semantic / difficulty factor / speed advice
2. 再分层实现：
   - 特征提取
   - 语义判断
   - sticky 决策
   - 命令建议
3. 再写约束：
   - 不读取 terrain label
   - 不依赖 privileged level
   - 不修改 scorer 统计

### 输出

`rewrite_plan.md` 每个模块至少写清楚：

- 为什么要重构
- 重构后边界是什么
- 哪些代码删除
- 哪些代码迁移
- 哪些参数保留
- 哪些风险被消除
